# Лабораторная работа 1: Основы работы с Git и GitHub

Репозиторий-шаблон для лабораторной работы по изучению базового рабочего процесса
разработки с использованием Git и GitHub: ветвление, коммиты, push, CI и Pull Request.

> ⚠️ **Репозиторий должен быть приватным.**
> При создании форка (или копии) убедитесь, что видимость репозитория — **Private**.
> Публичный репозиторий считается нарушением требований (см. раздел «Штрафы»).

> ⚠️ **Не делайте Push напрямую в `main`.** Вся работа ведётся в отдельной ветке.
> В `main` прямой push запрещён, изменения принимаются только через Pull Request
> с успешно прошедшим CI.

> ⚠️ **Pull Request создаётся в `main` ВАШЕГО (студенческого) репозитория.**
> PR в исходный (преподавательский) репозиторий-шаблон создавать **нельзя** —
> это нарушение (см. раздел «Штрафы»).

## 🎯 Цель работы

Освоить базовый рабочий процесс разработки с использованием Git и GitHub:

- клонирование репозитория и работа с ветками;
- осмысленные коммиты и push в удалённый репозиторий;
- работа с системой непрерывной интеграции (GitHub Actions);
- создание Pull Request и взаимодействие с CI-проверками.

## ✅ Что нужно сделать

1. **Создать собственный приватный репозиторий** на основе шаблона.
   - Через веб-интерфейс GitHub: **Use this template → Create a new repository**.
   - **Обязательно** выберите видимость **Private**.
   - Альтернатива: форк, после чего **сразу переведите репозиторий в Private**
     (Settings → General → Danger Zone → Change visibility → Make private).
2. **Клонировать** свой приватный репозиторий локально.
3. Создать ветку `feature/FIO-add-in-base.   
   3.1 Заполнить ФИО и группу в readme.md
4. **Реализовать функцию** `add_in_base` в файле `src/sum_in_base.py`.
5. Убедиться, что тесты проходят **локально**: `pytest -v`.
6. Сделать commit изменения **осмысленными коммитами** (минимум 2 коммита).
7. Сделать push ветки в удалённый репозиторий.
8. Убедиться, что **CI отработал успешно** (зелёная галочка на GitHub).
9. Открыть **Pull Request в `main` СВОЕГО репозитория** с описанием решения.
10. **Не мержить PR** — оставить открытым для проверки преподавателем.

## 📐 Требования к функции

Функция должна складывать два числа, записанных в системе счисления с заданным основанием.

### Сигнатура

```python
def add_in_base(a: str, b: str, base: int) -> str:
    ...
```

### Параметры

| Параметр | Тип   | Описание                                              |
|----------|-------|-------------------------------------------------------|
| `a`      | `str` | Первое число в виде строки, например `"1011"`         |
| `b`      | `str` | Второе число в виде строки, например `"111"`          |
| `base`   | `int` | Основание системы счисления, `2 <= base <= 36`        |

### Возвращаемое значение

Строка — сумма `a + b` в той же системе счисления.

### Примеры

```python
add_in_base("1011", "111", 2)   # -> "10010"
add_in_base("99", "1", 10)      # -> "100"
add_in_base("FF", "1", 16)      # -> "100"
add_in_base("Z", "1", 36)       # -> "10"
```

### Обработка ошибок

Функция должна выбрасывать `ValueError`, если:

- `base < 2` или `base > 36`;
- хотя бы один из операндов содержит символ, недопустимый для данной системы счисления.

## 🚀 Быстрый старт

### 1. Создание приватного репозитория

```bash
# Вариант А (рекомендуемый): через веб-интерфейс GitHub
#   1. Откройте страницу репозитория-шаблона.
#   2. Нажмите "Use this template" → "Create a new repository".
#   3. В поле "Repository name" укажите, например, sum-in-base.
#   4. В разделе "Visibility" выберите "Private".
#   5. Нажмите "Create repository".

# Вариант Б: форк с последующим переводом в приватный
#   1. Нажмите "Fork" в правом верхнем углу.
#   2. В настройках форка (Settings → General → Danger Zone)
#      переведите видимость в Private.

# Клонирование своего приватного репозитория
git clone https://github.com/<ваш-логин>/sum-in-base.git
cd sum-in-base
```

> 🔒 Проверьте, что на странице репозитория отображается метка **Private**
> рядом с названием. Если метки нет — репозиторий публичный, исправьте это
> в настройках.

### 2. Создание виртуального окружения

```bash
python -m venv .venv

# Linux / macOS
source .venv/bin/activate

# Windows (PowerShell)
.venv\Scripts\Activate.ps1

# Windows (cmd)
.venv\Scripts\activate.bat
```

### 3. Установка зависимостей

```bash
pip install --upgrade pip
pip install -r requirements.txt
```

### 4. Запуск тестов (должны упасть — это нормально)

```bash
pytest -v
```

Вы увидите ошибки `NotImplementedError` — так и задумано: функция ещё не реализована.

## 🧭 Пошаговая инструкция

### Шаг 1. Создайте рабочую ветку

```bash
git checkout -b feature/add-in-base
```

### Шаг 2. Реализуйте функцию

Откройте `src/sum_in_base.py` и напишите реализацию `add_in_base`.

### Шаг 3. Проверьте локально

```bash
pytest -v
```

Все тесты должны быть зелёными. Если нет — правьте код, а не тесты.

### Шаг 4. Закоммитьте изменения

```bash
git add src/sum_in_base.py
git commit -m "feat: реализована функция add_in_base"
```

> 💡 Рекомендуется делать несколько осмысленных коммитов, например:
> - `feat: добавлен скелет add_in_base`
> - `feat: реализовано сложение столбиком`
> - `fix: обработка неверного основания`

### Шаг 5. Запушьте ветку

```bash
git push -u origin feature/add-in-base
```

### Шаг 6. Проверьте CI

Перейдите на страницу **своего** репозитория на GitHub → вкладка **Actions**.
Убедитесь, что workflow для вашей ветки завершился успешно (зелёная галочка ✅).

> ⚠️ Если репозиторий приватный, GitHub Actions по умолчанию включён для
> приватных репозиториев на бесплатном плане (с ограничением минут).
> Если вкладка Actions пуста — проверьте Settings → Actions → General →
> "Allow all actions and reusable workflows".

### Шаг 7. Создайте Pull Request

1. На GitHub появится кнопка **"Compare & pull request"** — нажмите её.
2. **Убедитесь, что PR создаётся внутри ВАШЕГО репозитория:**
   - **base repository** = `<ваш-логин>/sum-in-base`
   - **base branch** = `main`
   - **compare branch** = `feature/add-in-base`
3. ❗ **Не создавайте PR в репозиторий преподавателя / исходный шаблон.**
   Если GitHub предлагает `base repository: <преподаватель>/sum-in-base` —
   это ошибка, измените base на свой репозиторий.
4. Заполните описание PR:
   - что сделано;
   - как проверялось (локальные тесты, CI);
   - возникшие сложности (по желанию).
5. Нажмите **"Create pull request"**.
6. **НЕ нажимайте "Merge pull request".**

### Шаг 8. Дождитесь CI на PR

На странице PR должен загореться зелёный статус проверки.
Если CI красный — исправьте код, закоммитьте и запушьте снова (PR обновится автоматически).

## ⚠️ Штрафы

| Нарушение                                                              | Штраф       |
|------------------------------------------------------------------------|-------------|
| Прямой push в `main`                                                   | −10 баллов  |
| PR смержен без указания преподавателя                                  | −5 баллов   |
| **Публичный репозиторий (видимость не Private)**                       | **−10 баллов** |
| **Pull Request создан в исходный (преподавательский) репозиторий-шаблон, а не в свой** | **−10 баллов** |

| Изменён файл `.github/workflows/ci.yml`                                | −5 баллов   |

| Не заполнено ФИО или группа                              | −5 баллов   |

## 📤 Что сдавать

1. **Ссылку на свой приватный репозиторий** (ваш логин GitHub).
   - Убедитесь, что преподаватель добавлен в **Settings → Collaborators**
     (или выдан доступ через организацию), иначе он не сможет проверить
     приватный репозиторий.
2. **Ссылку на открытый Pull Request** в `main` **вашего** репозитория.
   - Ссылка должна иметь вид:
     `https://github.com/<ваш-логин>/sum-in-base/pull/<номер>`.
   - Ссылка вида `https://github.com/<преподаватель>/sum-in-base/pull/<номер>`
     не принимается (штраф).
3. Скриншот зелёного CI (по желанию, но помогает быстрее получить оценку).

Отправьте материалы в LMS (ee.istu.ru).

> 🔑 **Не забудьте предоставить доступ преподавателю к приватному репозиторию.**
> Без доступа проверка невозможна, работа считается несданной.

## ❓ FAQ

**Q: Репозиторий обязательно должен быть приватным?**
A: Да. Публичный репозиторий — штраф −10 баллов. Переведите его в Private
в настройках (Settings → General → Danger Zone → Change visibility).

**Q: Я сделал форк, и GitHub предложил создать PR в репозиторий преподавателя. Это нормально?**
A: Нет. PR нужно создавать **в свой** репозиторий. При создании PR вручную
выберите в поле **base repository** свой логин, а не логин преподавателя.
PR в исходный шаблон — штраф −10 баллов.

**Q: Тесты падают с `NotImplementedError` — это нормально?**
A: Да. Функция ещё не реализована. Ваша задача — сделать так, чтобы тесты стали зелёными.

**Q: Я случайно запушил в `main`. Что делать?**
A: Это штраф.

**Q: CI красный, а локально всё зелёное. Почему?**
A: Проверьте, что запушили последние изменения, что CI использует ту же версию Python,
и что в репозиторий попали все нужные файлы (например, `requirements.txt`).
Для приватных репозиториев также проверьте, что Actions разрешён в настройках.

**Q: Мой PR кто-то должен смержить?**
A: Нет. PR должен остаться открытым. Преподаватель сам проверит и оценит.

**Q: Как перезапустить CI?**
A: CI запускается автоматически на каждый push в ветку PR. Просто сделайте новый коммит
и запушьте.

**Q: Можно ли редактировать тесты?**
A: Нет. Если нашли баг в тестах — сообщите преподавателю.

**Q: Преподаватель не видит мой приватный репозиторий. Что делать?**
A: Добавьте его в Settings → Collaborators (или выдайте доступ через организацию)
и пришлите ссылку повторно.
